1. Logging Plan

1.1 What to Log

The Beautiful Nail appointment scheduling system logs critical business events and system errors to ensure observability and rapid incident response. The following categories are logged:

  • Appointment Operations: Booking attempts, successful bookings, cancellations, confirmation notifications
  • Concurrency & Transaction Events: Retry attempts, slot contention, isolation level enforcement, version check failures
  • External Service Integration: Notification service calls, failures, timeouts, recovery attempts
  • System Errors: Database connection failures, transaction rollbacks, unexpected exceptions
  • Access Patterns: User authentication events, endpoint access (at DEBUG level)

2. Monitoring Metrics

The system tracks three critical metrics to monitor operational health and identify performance degradation in production.

2.1 Number of Bookings Per Hour

Purpose: Tracks business volume and user demand patterns over time.

Implementation: A counter metric increments each time an appointment is successfully booked. A scheduled task (every 60 seconds) records the cumulative count to a metrics log, resets the counter, and makes the data available via the /metrics/bookings endpoint.

Alert Threshold: If hourly bookings drop below 5 (indicating potential service outage), an WARNING is logged to alert operators.

2.2 Failed Bookings

Purpose: Identifies user experience issues and booking system reliability problems.

Implementation: A counter increments whenever a booking attempt fails (including all 3 retry attempts). Failures are categorized by reason (slot unavailable, database locked, service error). The metric is exposed via /metrics/bookings/failed with a breakdown by error type.

Alert Threshold: If the failure rate exceeds 10% of total booking attempts within a 5-minute window, an ERROR is logged and operators are notified.

2.3 Average Latency of Booking Operation

Purpose: Measures user-facing performance and identifies database or service bottlenecks.

Implementation: A timer captures elapsed time from the start of the booking request to successful completion (or failure). Latency samples are recorded in a rolling window, and the endpoint /metrics/bookings/latency provides mean, min, max, and p99 percentile latency values.

Alert Threshold: If p99 latency exceeds 5 seconds, a WARNING is logged. If p99 latency exceeds 10 seconds, an ERROR is logged indicating potential cascading failures.

3. Failure Scenario + Recovery Strategy

3.1 Failure Scenario: Notification Service Unavailable

Scenario Description: The external notification service becomes temporarily unavailable, causing booking confirmation emails to fail. Users complete the appointment booking successfully, but the confirmation notification cannot be sent. If recovery is not implemented, users will not receive confirmation details.

Sequence:

  1. User submits booking request at 14:30:00
  2. AppointmentService successfully reserves the slot and creates appointment record
  3. NotificationService attempts to call external API at notification.service.url
  4. External service returns HTTP 503 Service Unavailable
  5. Transaction currently active - notification failure occurs after slot is reserved

3.2 Recovery Strategy

A. Immediate Retry with Exponential Backoff

  • NotificationService implements up to 3 automatic retries with exponential backoff (1s, 2s, 4s)
  • Each retry attempt is logged at WARN level with attempt number and elapsed time
  • If all 3 retries fail, the exception is logged but NOT propagated (graceful degradation)

B. Asynchronous Queue Fallback

  • If notification fails after retries, the notification request is queued to an in-memory deque with a TTL of 24 hours
  • A background task runs every 30 seconds to attempt sending queued notifications
  • Successfully sent notifications are removed from the queue; failed ones are retried or discarded after TTL expires

C. User Notification via Alternative Channel

  • If notification service remains unavailable, users can retrieve their confirmation via the /appointments/<id>/confirmation endpoint
  • This ensures users can always access their booking details even if email notifications fail

D. Operational Alerting

  • After the first failed notification, a WARN is logged: "Notification service unavailable, retrying in X seconds"
  • After 3 consecutive failed notifications across different appointments, an ERROR is logged: "Notification service degraded; users may not receive confirmations"
  • This alert signals operators to investigate the external service health

A.4 Notification Service with Retry Logic

@Service public class NotificationService { private static final Logger log = LoggerFactory.getLogger(NotificationService.class); private final RestTemplate restTemplate; private final Queue<NotificationRequest> retryQueue = new LinkedList<>(); private final String notificationServiceUrl; public void sendConfirmation(Appointment appointment) { NotificationRequest request = new NotificationRequest(appointment); sendWithRetry(request); } private void sendWithRetry(NotificationRequest request) { int maxRetries = 3; int[] backoffMs = {1000, 2000, 4000}; for (int attempt = 0; attempt < maxRetries; attempt++) { try { restTemplate.postForObject(notificationServiceUrl, request, String.class); log.info("Notification sent successfully for appointment {}", request.getAppointmentId()); return; } catch (RestClientException e) { log.warn("Notification attempt {}/{} failed: {}", attempt + 1, maxRetries, e.getMessage()); if (attempt < maxRetries - 1) { try { Thread.sleep(backoffMs[attempt]); } catch (InterruptedException ie) { Thread.currentThread().interrupt(); } } } } // All retries failed - queue for later log.error("Notification failed after {} retries; queuing for async retry", maxRetries); retryQueue.offer(request); } @Scheduled(fixedDelay = 30000) // Every 30 seconds public void processRetryQueue() { while (!retryQueue.isEmpty()) { NotificationRequest request = retryQueue.poll(); try { restTemplate.postForObject(notificationServiceUrl, request, String.class); log.info("Queued notification sent successfully for appointment {}", request.getAppointmentId()); } catch (Exception e) { log.warn("Queued notification still failing; will retry later"); retryQueue.offer(request); break; } } } }
